# 運用とデータ契約

## データの保存

SQLiteの `sessions`、`messages`、`tasks` が現在の状態、`events` が追記形式の監査履歴。各状態更新とイベントは同じトランザクションで確定する。WALと `synchronous=FULL` を使用する。秘密値はログに保存しない。メッセージ本文にはプロジェクト情報が含まれるため、DB・バックアップへのアクセスを管理する。

イベント形式は `{ seq, version, type, time, data }`。`seq` は全体で単調増加するカーソル。イベントを削除しない限り `/api/events?after=<seq>&limit=100` で履歴を再取得できる。各メッセージは `id`、返信チェーンを表す `threadId`、`replyTo`、任意の `taskId` を持つ。送信時のセッション設定をスナップショットとして保持する。

## 配信状態

| 状態 | 意味 |
|---|---|
| queued | 送信意図と本文をDBに保存した |
| delivering | アダプターへ配送を開始した |
| accepted | 相手のInboxで受付された。モデルの処理完了ではない |
| processing | 受信セッションが処理開始を明示報告した |
| completed | 受信セッションが依頼の処理完了を明示報告した |
| failed | 相手が未受付であることを確認できる配送失敗 |
| uncertain | 受付済みか確定できない。相手で確認するまで再送しない |

`processing` / `completed` は実行エージェントの報告であり、独立した検証結果ではない。タスクの `completed` とも別。初期実装は自動再送しない。`queued` は起動後に配送されるが、停止時に `delivering` だったものは `uncertain` になる。

## DBの単一オーナーと停止

DBを開く際に `<database>.lock/owner.json` を作成する。同じファイルの二重オープンを拒否する。正常終了では配送中の操作とHTTPサーバーを終了してDBを閉じ、ロックを削除する。強制終了でロックが残った場合は、**該当ホストのオーナープロセスが停止していることを確認してから**ロックディレクトリを手動削除する。起動中のプロセスのロックを削除しない。

バックアップはオーナーを正常停止してからDBをコピーする。稼働中のSQLiteファイルだけを単純コピーしない。マイグレーション前にも同様にバックアップする。現時点で保持期間・アーカイブ・自動ローテーションは未実装。

## タスク管理

更新には最新の `revision` を渡す。古い更新は `STALE_REVISION` で拒否される。作成・担当変更・再送はtowerのみ。更新はtowerか現在の担当者が行う。レビュー情報はreview役またはtowerのみ、CI情報はtowerのみが記録できる。

`kind: implementation` の完了には `headSha`、同SHAの `reviewedSha` と `review: approved`、`ci: passed` が必要。`headSha` が変わると以前のレビューとCIを消去し、完了済みタスクはreviewへ戻る。仕様タスクの完了にはコードのSHAを要求しない。依存元が後で再開された場合の依存先の再開や、仕様版変更の影響範囲判断はtowerが行う。

## HTTP

- `GET /`、`GET /viewer.js`: データを含まない閲覧画面。
- `GET /api/snapshot`: Bearer認証。全セッション、タスク、直近200件の通信、最新seq。
- `GET /api/events`: Bearer認証。最大500件の履歴ページ。
- `POST /webhooks/github`: GitHub HMAC-SHA256署名認証。上限1 MiB。

viewerトークンはブラウザーのメモリーだけに保持し、URLやlocalStorageには保存しない。画面は約2秒ごとに更新する。画面に出す本文は `textContent` で描画する。HTTP APIに任意の送信元で状態を変更するエンドポイントは設けない。

GitHubイベントは署名とリポジトリ許可を確認して通知する。CI通知は複数run・再実行・対象SHAの対応付けが必要なため、この版では自動でタスクを完了させない。

## 制限値

既定の本文上限65,536バイト、待機中の配送上限1,000件、返信チェーン上限32件、送信元ごとの新規送信毎分60件。冪等キーの同一再試行は新規送信として数えない。配送完了を自動検出しないため、長時間processingの通知や期限監視は今後追加する。
